## What I built

2 of the "groundbreaking innovations" requested by the user, both backed by

### Innovation 1: Adversarial AI Self-Attack

An AI agent whose only job is to find blind spots in GuardianX's own
detection. It generates 5-10 synthetic vulnerable code snippets that
*should* be flagged, runs them through the existing scan logic (regex-
based, intentionally has gaps), and if GuardianX misses any, the AI
auto-writes a new detection rule + saves it to the `DetectionRule` table.

**Files:**
- `prisma/schema.prisma` + `prisma/schema.production.prisma` — added the
  `DetectionRule` model (with `@@index` for autoGenerated/isActive/
  language+severity).
- `src/app/api/self-attack/route.ts` (POST + GET) — auth-required. Picks
  a deterministic-but-rotating subset of 5-10 snippets from the
  hardcoded 24-pattern vuln library (SQLi, XSS, SSRF, path traversal,
  command injection, deserialization, hardcoded secrets, weak crypto,
  prototype pollution, ReDoS, XXE, open redirect, timing attacks, JWT
  'none' alg, Python pickle.loads, etc.). For each snippet, runs the
  existing scan logic. If missed, calls `chatWithFallback` from
  `@/lib/llm` to generate a new detection rule (with heuristic regex
  derivation fallback per vuln pattern). Saves the rule with
  `autoGenerated: true`. Audit-logs the run for history.
- `src/app/api/self-attack/runs/route.ts` (GET + PATCH) — auth-required.
  GET returns last 20 self-attack runs (decoded from `AuditLog` rows
  with `action="self-attack.run"`) + the full list of auto-generated
  DetectionRule rows + totals. PATCH toggles `isActive` on a rule.
- `src/components/sentinel/adversarial-ai.tsx` — full-screen tab view.
  Header with pulsing red dot + SELF-ATTACKING badge. Big "Run Self-
  Attack" button. Animated terminal showing each snippet being scanned
  with PASS/FAIL badges (revealed one-by-one via setInterval stagger).
  Summary card showing "Tested N · Missed M · Rules Added K" + new
  rules list with name + severity + CWE. Auto-generated rules list
  with Activate/Deactivate toggles (shadcn Switch). History table of
  past 20 runs (responsive: table on desktop, stacked cards on
  mobile). Dark theme, red/emerald accents, hud-corners.

### Innovation 2: APT Persona Engine

AI role-plays as specific threat actor groups (Lazarus, APT29, FIN7,
Anonymous Sudan, etc.) and simulates how THEY would attack the user's
codebase — using their known TTPs, preferred vuln classes, and tooling.

**Files:**
- `src/lib/apt-personas.ts` — exports 11 real APT personas (Lazarus,
  APT29, APT28, FIN7, APT41, Sandworm, Equation Group, Anonymous Sudan,
  Lapsus$, Scattered Spider, Mustang Panda) each with origin/flag/motivation/
  ttps/preferredVulns/knownFor/sophistication/color/description + a
  PERSONA_COLOR_MAP and SOPHISTICATION_COLOR helper.
- `src/app/api/apt-simulate/route.ts` (POST) — auth-required. Body:
  `{ codebaseId, personaId }`. Builds the persona system prompt ("You are
  {persona.name}, a {persona.sophistication}-sophistication threat actor
  group from {persona.origin}. Your known TTPs are {persona.ttps}. Your
  preferred vulnerability classes are {persona.preferredVulns}. You're
  known for {persona.knownFor}. Analyze this codebase and tell me how YOU
  would attack it, step by step, using your specific TTPs."). Calls
  `chatWithFallback`. Returns `{ persona, attackPlan, summary,
  codebaseName, generatedAt, provider, usedFallback }`. Heuristic
  fallback walks the source code looking for the persona's preferred
  vuln classes + builds a 5-step kill chain derived from the persona's
  TTPs — so the simulator always returns a useful plan, even with no LLM.
- `src/components/sentinel/apt-persona-engine.tsx` — full-screen tab
  view. Grid of 11 persona cards (name, alias, flag, sophistication
  badge, "Simulate Attack" button). Clicking opens a codebase selector
  Dialog (loads codebases from /api/codebases). Running the simulation
  shows a kill chain viz (recon → initial_access → execution →
  persistence → exfiltration) with each step's TTP, target, vuln class,
  exploit prose, and likelihood bar. Prose summary card: "If {persona}
  targeted {codebase}, they would likely..." Dark theme, color per
  persona, hud-corners.

## Key decisions

1. **DetectionRule model**: Added to BOTH `schema.prisma` (SQLite for
   dev) and `schema.production.prisma` (PostgreSQL for prod) so they stay
   in lockstep (per existing comment convention in the schema).
2. **Self-attack run history**: No dedicated `SelfAttackRun` model — I
   reused the existing `AuditLog` table with `action="self-attack.run"`
   and a JSON `details` payload (containing testedCount, missedCount,
   rulesAdded, runRows, report). This avoids adding another Prisma model
   outside my scope while still giving the history route queryable data.
3. **Rule activation toggle**: No new route — extended the existing
   `src/app/api/self-attack/runs/route.ts` with a PATCH handler that
   toggles `isActive` on a rule by `ruleId`. Both POST + PATCH are in the
   same file (within my scope).
4. **Vuln library**: 24 hardcoded patterns (10 caught by existing logic
   for positive coverage + 14 missed blind spots the adversarial AI is
   supposed to discover). Includes JS + Python examples spanning 14
   vulnerability classes (SQLi, XSS, SSRF, path traversal, command
   injection, deserialization, prototype pollution, ReDoS, XXE, open
   redirect, JWT 'none', timing attacks, hardcoded creds, weak crypto,
   weak RNG).
5. **Existing scan logic**: 12 regex patterns that intentionally miss
   ~14 of the 24 vuln patterns. This gives the adversarial AI real
   work to do every run (real misses → real rule writes).
6. **LLM rule validation**: For each LLM-generated rule, the route
   compiles the regex with `new RegExp(...)` and verifies it actually
   matches the source snippet before persisting. If the LLM returns a
   broken regex or one that wouldn't match, the route falls back to
   the heuristic derivation.
7. **Idempotency**: Before adding a rule, checks whether a rule with
   the same name (or CWE+language) already exists — skips if so. This
   prevents rule duplication across re-runs of the same vuln.
8. **Rotating subset**: The route picks a rotating subset of 7-10 vulns
   per run (deterministic by hour bucket). The order changes every hour
   so re-runs surface different blind spots over time without
   completely invalidating prior rules.
9. **APT personas**: 11 real groups sourced from MITRE ATT&CK + Mandiant +
   CrowdStrike public reporting. Each persona's preferred vulns drive the
   heuristic fallback's detection regexes when the LLM is unavailable —
   so the simulator returns a persona-flavored plan even on Vercel
   (where Z.AI SDK is unreachable).
10. **Kill chain viz**: Vertical timeline with phase-icon per step
    (Eye for recon, Lock for initial_access, Play for execution,
    Database for persistence, GitFork for exfiltration). Each step shows
    TTP + target + vuln class + exploit prose + likelihood bar. Color
    per phase (cyan→amber→rose→violet→red) following the no-indigo/blue
    constraint.
