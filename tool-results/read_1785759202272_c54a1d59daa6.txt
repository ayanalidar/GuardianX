   315→## Notes on the report download auth flow
   316→The existing `client-detail.tsx` "Generate Report" button did `window.open('/api/engagements/.../report', '_blank')`. This opens a new tab which does NOT carry the `Authorization: Bearer` header from localStorage. The middleware blocks the request with a 401, so the button was effectively broken (the new tab would show a 401 JSON error). The new implementation uses authenticated `fetch()` (which DOES carry the header because it runs in the same page context), converts the response to a `Blob`, creates an object URL via `URL.createObjectURL()`, and opens THAT in a new tab. The blob URL inherits the origin so it works in any browser. The object URL is revoked after 60 seconds to avoid memory leaks. The same pattern is used for the portal's "Download Report" button (with `portal-token` instead of `guardianx-token`).

   318→## Notes on the engine PDF fallback
   319→The Railway sentinel-engine spawns `python3 scripts/generate-vapt-report.py` to produce the PDF. This requires python3 + ReportLab to be installed in the engine container. In dev/preview environments where the engine is unreachable (port 3003 not bound, or the engine container not running), the existing PDF route returned a JSON error like `{ "error": "Engine unreachable" }`. The new fallback issues a 307 redirect to `/api/engagements/[id]/report-html`, which serves a fully self-contained HTML report. The browser follows the redirect automatically, and the user gets a printable report they can save to PDF via `Cmd/Ctrl+P`. This makes the "Generate Report" button always produce a deliverable.

   659→## Task #2 — Per-IP + per-endpoint rate limiting on auth routes
   660→
   661→**Agent:** general-purpose
   662→**Task ID:** #2-per-ip-rate-limit
   663→**Date:** 2024
   664→**Status:** complete
   665→
   666→### Summary
   667→Replaced the previous **global** auth rate-limit bucket (one `ip` key shared across ALL `/api/auth/*` routes — 10 req / 15 min) with **per-IP + per-endpoint** buckets. Each auth endpoint now has its own independent counter per IP, keyed `${ip}:${routeType}`, so hammering `/api/auth/login` no longer burns `/api/auth/signup`'s quota. Endpoint-specific thresholds were chosen to match the threat model (brute-force vs. signup abuse vs. email enumeration). The in-memory `rateStore` Map is retained (Edge runtime — no Redis/Upstash dependency), and this tradeoff is now documented in a comment. 429 responses now name the limit that was hit (e.g. "Too many signup attempts") and include a `Retry-After` header + `retry_after` / `limit` fields.
   668→
   669→### Files modified
   670→
   671→**`src/lib/rate-limit.ts`**
   672→- Added exported helper `getAuthRateLimitConfig(path: string): { windowMs: number; maxReqs: number } | null`.
   673→  - Returns `null` for any path outside `/api/auth/*` (middleware then falls back to the generic 300/min API bucket).
   674→  - Switch on the exact path returns endpoint-specific thresholds (see table below).
   675→  - Default case covers any other `/api/auth/*` route (e.g. `/session`, `/logout`) at 20 req / 15 min.
   676→- Annotated the existing `applyAuthRateLimit` as a legacy single-bucket limiter, retained for any route handler that wants a second defense layer.
   677→
   678→**`src/middleware.ts`**
   679→- Imported `getAuthRateLimitConfig` from `@/lib/rate-limit`.
   680→- Added module-private helpers `authRouteType(path)` (derives the `routeType` slug from the auth path, e.g. `/api/auth/forgot-password` → `forgot-password`) and `limitLabel(routeType)` (maps to a human-readable name for the 429 body).
   681→- Rewrote the rate-limit block:
   682→  - Looks up `authConfig = getAuthRateLimitConfig(path)`.
   683→  - If auth route → `rateKey = ${ip}:${routeType}`, uses the config's `windowMs`/`maxReqs`.
   684→  - Else → `rateKey = ${ip}:api`, 300 req / 60s (unchanged generic API bucket).
   685→  - 429 response body: `{ error: "Too many <limitName> attempts. Rate limit exceeded. Please try again in N seconds.", retry_after: N, limit: <limitName> }` with `Retry-After: N` header.

   687→
   688→### Rate-limit thresholds chosen (per IP)
   689→
   690→| Endpoint | Limit | Window | Rationale |
   691→|---|---|---|---|
   692→| `/api/auth/login` | 10 req | 15 min | Brute-force protection on passwords |
   693→| `/api/auth/signup` | 5 req | 60 min | Signup abuse — creates durable user + triggers outbound email (strictest) |
   694→| `/api/auth/forgot-password` | 5 req | 60 min | Email enumeration protection (endpoint sends email if account exists) |
   695→| `/api/auth/reset-password` | 10 req | 15 min | Brute-force on reset tokens |
   696→| `/api/auth/verify-email` | 10 req | 15 min | Brute-force on verification codes (route added speculatively; not yet implemented) |
   697→| other `/api/auth/*` (session, logout, …) | 20 req | 15 min | Catch-all |
   698→| non-auth `/api/*` | 300 req | 60 s | Unchanged — dashboard fires ~12 concurrent fetches on mount + 10s auto-refresh |
   699→
   700→### 429 response shape
   701→```json
   702→{
   703→  "error": "Too many signup attempts. Rate limit exceeded. Please try again in 3573 seconds.",
   704→  "retry_after": 3573,
   705→  "limit": "signup"
   706→}
   707→```
   708→With header `Retry-After: 3573`. The `limit` field lets clients branch on which bucket was hit.

   714→- `rateStore` stays in `src/middleware.ts` (not migrated to the lib's `store` Map) per the task's "keep the in-memory store" instruction.

   719→### Known tradeoffs / future work
   720→- **Per-Edge-instance counters**: on Vercel Edge Functions, N warm instances = up to N× the nominal limit reachable by a determined attacker. Accepted for MVP.    811→## Summary
   812→Instrumented 9 sensitive API routes (covering 11 distinct audit actions) with `AuditLog` inserts that fire AFTER the primary DB operation succeeds.    921→## Task #5-session-revocation — Per-user JWT session revocation via `tokenVersion`
   922→
   923→**Agent:** general-purpose
   924→**Task ID:** #5-session-revocation
   925→**Date:** 2024
   926→**Status:** complete
   927→
   928→## Problem
   929→JWTs are stateless and valid for 7 days. The only way to invalidate a specific user's token was rotating `JWT_SECRET`, which logs out EVERY user. There was no per-user revocation: if an admin's credentials were stolen, or a user clicked "Log out" on one device, the existing JWT remained technically valid (signature + expiry) until the 7-day TTL expired.
   930→
   931→## Approach
   932→Implemented per-user session revocation using a `tokenVersion` counter column on the User table.
   933→
   934→- Every issued JWT embeds the user's current `tokenVersion` (default 0).
   935→- To revoke all of a user's sessions, increment `User.tokenVersion` in the DB.
   936→- Sensitive Node.js API routes compare the JWT's `tokenVersion` against the DB's current value via the new `enforceSessionRevocation(req)` helper. On mismatch → 401 `SESSION_REVOKED`.
   937→- Edge middleware CANNOT do this check (no DB access in Edge runtime), so revocation is enforced ONLY in Node.js API routes that opt in. This is intentional: the most sensitive routes (user management, settings, approve) get the check, while high-throughput read routes (dashboard stats, feeds) skip the extra DB round-trip.
   938→
   939→The third (least invasive) approach from the task spec was taken: `requireAuth` stays sync (so the dozens of existing callers are untouched), and a new async `enforceSessionRevocation(req)` helper is called after `requireAuth` only in routes that opt in.
   940→
   941→## Files created
   942→
   943→### 1. `src/app/api/auth/revoke-sessions/route.ts` (new, ~150 lines)
   944→POST endpoint that increments a user's `tokenVersion` by 1.
   945→- **Auth**: requires a valid JWT (admin or self). Admins can revoke any user; non-admins can only revoke their own (`caller.userId === body.userId`).
   946→- **Body**: `{ userId: string }`. 400 if missing, 404 if user not found.

  1130→### Design decisions
  1131→
  1132→- **Fire-and-forget, not awaited:** A login-attempt insert failing must never block the user's login or change the response. The `void (async () => {...})()` pattern (already established in `revoke-sessions/route.ts`) guarantees this — the IIFE is never awaited and any error is caught inside and logged.
  1133→- **No row for unknown emails:** Creating a LoginHistory row keyed by the supplied email would let an attacker enumerate accounts via `/api/auth/login-history` (hit `/api/auth/login` with a guessed email, then check if a row appeared). We only create rows for attempts against a known user account. The trade-off is that brute-force attempts against non-existent emails aren't auditable here — but they're already noisy in server logs and don't compromise any real account.
  1134→- **2FA step-up counted as success:** When `/api/auth/login` returns `requiresTwoFactor`, the password was verified — that's a successful password authentication. The 2FA challenge itself is a separate event handled by `/api/auth/2fa/login` (out of scope for this task). Logging it as `success=true` is correct: the user's password worked.
  1135→- **RLS enabled on LoginHistory (the only such table):** Defense-in-depth. The backend uses the `service_role` key which bypasses RLS, so application-level queries see all rows. But if the anon/authenticated key ever leaked to the client, the SELECT policy restricts anon queries to rows whose `userId` matches the JWT `sub` claim — so an attacker with the anon key couldn't read other users' history. This is the ONLY table in the GuardianX schema with RLS enabled (per the worklog, every other table has `DISABLE ROW LEVEL SECURITY`).
  1136→- **No FK constraint on `userId`:** Prisma's `@relation` would add a FK, but Supabase's REST API doesn't enforce FKs the same way, and an FK would make inserts slower (extra constraint check) and would cascade-delete history when a user is deleted (we want to KEEP audit history even if the account is later removed — it's evidence). The application layer guarantees `userId` is real (it's read from the User row immediately before the insert).
  1137→- **UA truncation to 512 chars:** Real browser UAs are ~250 chars. 512 leaves headroom for unusual but legitimate UAs while capping the column against malicious bot UAs that try to bloat the table with megabytes of SEO spam.
  1138→- **No geolocation / country detection:** Task spec explicitly said to skip this (would need an external IP-geolocation API). The raw IP is shown — if the user wants to investigate further, they can plug the IP into a public IP-lookup service.
  1139→- **Failure reasons are a fixed enum:** "Invalid password", "Email not verified", "Pending approval". Internal errors (DB outage, unexpected exception) don't get a LoginHistory row at all (because we throw before reaching the `recordLoginAttempt` call). This keeps the audit log clean and free of leaky stack-trace text.

  1195→- **`sanitizeText(input: string, maxLength: number = 1000): string`** —

  1211→  sanitizer on untrusted HTML.

  1470→### Design decisions
  1471→
  1472→- **No double-logging.** `sendEmail` internally calls `_sendMailWithConfig` (the private, non-logging variant) — NOT the public `sendEmailWithConfig`. This means each email send produces exactly one EmailLog row, whether it went through `sendEmail` (production) or `sendEmailWithConfig` (test email). The alternative — having `sendEmail` call `sendEmailWithConfig` and both log — would have produced two rows per SMTP send.
  1473→- **Fire-and-forget logging.** `logEmail` returns `Promise<void>` and is `void`-tagged at every call site. A DB outage never blocks an outgoing email or the API response that triggered it. Errors are logged to stdout (`[email] EmailLog insert failed: ...`) but never thrown.
  1474→- **Metadata only.** Only `to`, `subject`, `status`, `messageId`, `error`, `template` are stored. Never the email body, never the SMTP password, never any other credential. `subject` is defensively truncated to 500 chars and `error` to 2000 chars to prevent oversized rows.
  1475→- **Dev-mode sends are logged.** When SMTP is not configured (local dev / preview), `sendEmail` returns `true` and logs an EmailLog row with `status: "sent"`. This keeps the panel populated and useful in environments without SMTP, so the operator can see that emails are being attempted even when they're only going to stdout.
  1476→- **Summary computed over last 50, independent of `?status=` filter.** The API runs two parallel `head:true` count queries (sent, failed) each capped at 50 rows. The headline success rate stays stable even when the operator narrows the table with `?status=failed` to investigate a problem. `successRate` is `null` when there are zero logs (UI shows "—").
  1477→- **60s auto-refresh.** The task spec explicitly said "not 10s — avoid memory pressure". 60s is fast enough to catch a delivery failure within a minute, but slow enough that an admin leaving the tab open doesn't generate meaningful DB load.
  1478→- **Silent background-poll failures.** If the 60s background refresh fails (transient network blip), the panel shows an inline amber banner ("Live refresh unavailable") instead of spamming toasts. Manual "Refresh" button failures DO show a toast, since the user explicitly asked.
  1479→- **RLS disabled on EmailLog.** The backend uses the `service_role` key (which bypasses RLS), and admin-only access is enforced in `/api/email-logs` via `requireAdmin` + `enforceSessionRevocation`. This matches the pattern used by every other audit-style table in the schema (`AuditLog`, `CredentialAudit`, etc.). The only table with RLS enabled is `LoginHistory` (Task #12), which has a stricter per-user visibility requirement.
  1480→- **Template naming convention.** Lowercase camelCase, matching the existing `ONBOARDING_SUBJECTS` keys where applicable (`welcomeAdmin`, `welcomePending`, `passwordReset`, `passwordResetSuccess`, `emailVerification`, `accountApproved`, `accountRejected`). New templates: `dailyDigest`, `weeklyDigest`, `notification`, `smtpTest`.

  1503→## Task #4 — Memory pressure mitigation (slow polling + pause on hidden tab)
  1504→
  1505→**Agent:** general-purpose
  1506→**Task ID:** #4-memory-pressure
  1507→**Date:** 2024
  1508→**Status:** complete
  1509→
  1510→### Problem
  1511→The dashboard (`src/app/page.tsx` → `<CommandCenter>`) auto-refreshes many
  1512→API endpoints in parallel. Each sub-panel ran its own `setInterval(load, …)`
  1513→independently, with intervals ranging from **3 s** (`process-tree`) to **15 s**
  1514→(`command-center`), and several at **5 s / 10 s**. Combined, the dashboard
  1515→tab alone was firing ~10 fetches every few seconds — and continued firing
  1516→even when the user had switched to another browser tab. On a 3.9 GB box the
  1517→dev server (`next-server`) was getting **OOM-killed at 2.8 GB**.
  1518→
  1519→### Approach
  1520→1. **Slow background polling to 30 s.** Every `setInterval(load, …)` in the
  1521→   dashboard surface (and the other tool tabs) now uses a 30 s cadence (or
  1522→   slower, where the original was already slower — e.g. threat-intel stays
  1523→   at 120 s, threat-briefing at 300 s).
  1524→2. **Pause polls when the tab is hidden.** A new `useVisiblePolling` hook
  1525→   wraps the Page Visibility API. When `document.hidden` is true, the
  1526→   interval is cleared; when the tab becomes visible again, the loader
  1527→   fires once to catch up and then resumes the 30 s cadence.
  1528→3. **Lazy-loading verification.** Confirmed that `src/app/page.tsx` already
  1529→   lazy-loads panels via conditional rendering — each tab branch only mounts
  1530→   its own panel(s), so switching tabs unmounts the previous panel and its
  1531→   polling effect cleanup runs (interval cleared, visibility listener
  1532→   removed). No code change needed; the existing pattern is correct.
  1533→
  1534→### Files created
  1535→1. **`src/hooks/use-visible-polling.ts`** — the shared hook. Signature:
  1536→   ```ts
  1537→   useVisiblePolling(fn, intervalMs, { enabled?, immediate? })
  1538→   ```
  1539→   - Calls `fn` once on mount (unless `immediate: false`), regardless of
  1540→     visibility, so a panel loaded in a background tab still has data when
  1541→     the user switches to it.
  1542→   - Starts `setInterval(fn, intervalMs)` only while
  1543→     `document.visibilityState === "visible"`.
  1544→   - On `visibilitychange` → hidden: clears the interval.
  1545→   - On `visibilitychange` → visible: calls `fn` once (catch-up), then
  1546→     restarts the interval.
  1547→   - `enabled: false` fully suspends polling (used in `page.tsx` to pause
  1548→     the patches auto-refresh while a scan is actively running — the scan
  1549→     poll handles refreshes during scanning).
  1550→   - The callback is stored in a `useRef` (updated in an effect, not during
  1551→     render, to satisfy `react-hooks/refs`) so it can change every render
  1552→     without restarting the interval.
  1553→   - Manual "Refresh" buttons keep working — they call `load()` directly,
  1554→     independent of this hook.
